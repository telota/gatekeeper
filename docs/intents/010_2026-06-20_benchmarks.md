# Benchmarks

2026-06-20

**Status: finished** 

## Tasks

Wir benötigen ein paar Benchmarks für den Gatekeeper, um die Ressourcenkosten einordnen zu können.
Mir schwebt ein synthetischer Bot-Sturm zu, den wir aber möglichst realistisch gestalten wollen.
Vorschlag: wir nehmen ein NGINX-Docker-Image und versehen es mit dem Gatekepeer und `hey`. Zunächst schicken wir über einen Zeitraum von 5 Sekunden insgesamt 10k Requests gegen eine ungeschützte NGINX-Location, um die Basisbelastung zu ermitteln. Anschließend schicken wir dei 10k gegen eine mit dem Gatekeeper abgsicherte Location ohne Cookie. Hier wird der Fast Path greifen, weil Rust nicht hashen muss. Danach fahren wir eine 3. Simulation mit einem Cookie, der Rust zum Hashen zwingt. Der muss nicht korrekt sein. Da wir mit constant time Vergleich arbeiten, ist die Prüfung immer gleich teuer. Wir müssen aber beachten, dass der Cookie mit einem UNIX-Timestamp im Klartext (30 Tage in der Zukunft), gefolgt von einem Doppelpunkt und einem für einen HMAC typischen String versehen sein muss - sonst verzerren wir das Ergebnis, weil der Gatekeeper den Cookie noch vor dem Hashen verwerfen würde.
Während der 3 synthetischen Angriffe wollen wir die CPU- und RAM-Auslastung beobachten, wobei uns natürlich vor allem NGINX und der Gatekeeper interessieren.
Idealerweise wird der Der Docker-Container gestartet, die 3 Tests mit kurzer Verzögerung ausgeführt, die Logs in eine Datei überführt und der Container anschließend geschlossen.

## Additions

Folgende Features wurden im Zuge der Implementierung zusätzlich eingeführt, um den Praxisbezug und die Analysequalität zu steigern:
- **Docker Compose Integration**: Kapselung des Benchmarks in Compose statt nacktem `docker run`, inklusive einfacher Volume-Mounts für Messergebnisse auf dem Host.
- **Ressourcen-Limitation**: Künstliche Begrenzung des Testcontainers auf **2 vCPUs und 2 GB RAM** via Compose, um den Betrieb auf einer typischen kleinen Produktions-VM realitätsnah zu simulieren.
- **Dynamische Host-Metriken**: Automatische Ermittlung von CPU-Modell, Prozessorkernen, RAM und Kernel-Version des Hostsystems aus `/proc` innerhalb des Containers für bessere Vergleichbarkeit.
- **ASCII-Tabellengenerierung**: Der Report wird nun mit einer fest breiten ASCII-Tabelle generiert, die in jedem Markdown-Viewer und im Terminal direkt formatiert lesbar ist.
- **Real-World Amortisationsmodell**: Mathematische Herleitung im Report, ab wann (Blockierungsrate) sich der Performance-Overhead ("Success Tax") durch die eingesparte Backend-Last amortisiert.
- **Lastprofil-Anpassung**: Umstellung von statischen 10k Requests auf ungedrosselte Last mit **100 parallelen Workern über 10 Sekunden** (`10s-100con`), um das System an die Sättigungsgrenze zu treiben.

## Debriefing

### Ausführung
Der Benchmark wird über Docker Compose direkt vom Projekt-Root-Verzeichnis aus gebaut und gestartet:
```bash
# 1. Gatekeeper Release-Binary lokal kompilieren
cargo build --release

# 2. Benchmark ausführen (erzwingt Rebuild des Docker-Images für Skript-Änderungen)
sudo docker compose -f benchmark/compose.10s-100con.yml up --build
```

### Ergebnisse
Die Messergebnisse werden als Markdown-Report mit Zeitstempel im Verzeichnis `benchmark/results/` abgelegt:
- Format: `benchmark/results/10s-100con_YYYYMMDD_HHMMSS.benchmark.md`
- Eine ausführliche Auswertung der Latenzen und Systemressourcen inklusive mathematischer Herleitung der Amortisationspunkte basierend auf einem Benchmark ist in `docs/reports/performance-audit_2026-06-22.md` dokumentiert.
